# 验证、验收与复用

Owner：本文件。Rule ID：EVIDENCE-01 / ACCEPTANCE-01。

| 层级 | 可证明的范围 |
| --- | --- |
| L0 | 静态代码、配置、资源引用、文本与绑定证据 |
| L1 | 构建、编译、自动化测试 |
| L2 | 本地运行、编辑器 Play Mode、可交互模拟或集成环境 |
| L3 | 目标平台开发者工具、模拟器或官方 sandbox |
| L4 | 已部署预览、体验版、测试/staging 环境 |
| L5 | 目标真机、真实账号、生产等价网络与生命周期 |

按实际能力与最低目标环境选择验证。最高层级不自动证明所有能力或所有低层级。helper 单元测试不能代替 caller/binding；模拟广告不能证明真机 SDK；静态 Hook 测试不能证明 Codex 已加载，更不能证明模型遵守规则。

可逆低影响改动检查实际差异即可；有意义的行为验证覆盖相关正例、反例、边界和失败路径。测试必须检查需求，不能仅镜像实现，不为使测试通过偷改需求。修改后核对范围并执行必要检查；通过且完成条件满足时交付，只有新改动、失败或实际风险才扩大验证。

交付说明行为变化、实际验证环境和结果、未覆盖的关键缺口。没有执行的检查不得写通过。结构 preflight 只证明文件、入口、版本和激活字段存在，不证明玩法、平台后台或业务验收。

只有用户明确确认具体能力在具体环境可用时，项目 owner 才记 UserAccepted，附日期、能力、版本、环境、限制及失效条件。测试通过、Ready、安装成功与用户沉默均不算验收。缺目标环境时交付现有成果并清楚说明最小后续验证。

验收能力可进入项目能力样例索引：保留最小复现、代码/资源/配置 owner、输入输出、接入前置、版本、验证/验收和失效条件。复用时重新核验环境与模块边界，跨项目可用性必须有另一个真实接入证据；此前只标 Golden Candidate，不宣称通用成熟组件。
