# 设计、性能与审查

Rule ID：DESIGN-01。仅按当前问题读取对应部分。

## UI 与视觉对齐

先确认目标用户、主要动作、画面信息层级及现有设计语言。有参考图时对照实际画面，区分已接受基线与待讨论方向；不能仅凭元素名称相同称为还原。布局、字体、间距、状态反馈、遮挡、点击和返回都应对应真实对象。自适应要核验目标尺寸、长文本与输入方式，不把开发机截图当全平台验收。

视觉修改保护原交互和已接受部分。方案可以解释取舍，审美选择由用户决定；自动化通过不代替视觉接受。

## 架构与复用

先找真实耦合点、变化原因、调用方和生命周期。能局部修复就不重做整层；新增接口必须服务当前至少一个真实边界。平台实现放 adapter，业务规则放领域 owner，资源和 UI 绑定保持可定位。候选组件标明依赖、配置、限制与验证环境，未经另一个实际项目接入不宣称跨项目成熟。

## 性能

先记录可重现负载、设备、版本及基线，再区分 CPU、GPU、内存、IO、分配或网络。按证据优化热点，每轮保留相同负载与前后指标。不能通过减少必要动作、改变玩法、降低已接受画质或改变计时语义制造“提升”。出现这些取舍时让用户决定。

缓存、资源生命周期和批量对象适配按 [game-methods.md](game-methods.md) 的实际适用部分；普通代码不要被迫引入缓存。

## 审查

围绕需求、行为、调用/配置、边界、可维护性与目标环境查实质问题。每项发现应有严重程度、可定位证据、触发条件、影响和可行修复；不要把个人偏好当缺陷。只读审查不顺手修复。没有发现不代表所有目标环境已通过；说明范围与证据上限即可。
