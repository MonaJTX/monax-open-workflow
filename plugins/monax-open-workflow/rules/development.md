# 通用开发流程

适用于软件、工具和游戏的需求、实现、修复。Rule ID：REUSE-01 / MINIMAL-01。

## 确定本次结果

从用户实际请求和项目现状确认目标、受影响对象、可观察的完成条件。区分讨论、只读审查和执行；请求式问法不自动等于只讨论，明确“不要改”也不能被行动关键词覆盖。权限归 [boundaries.md](boundaries.md)。

读取项目索引与匹配的长期约束，核验实际入口、调用链、配置和已有改动。只补会改变判断的缺口，不要求每个机械修改写一份方案。复合任务保留原目标，不能通过悄悄缩小交付范围来宣布完成。

## 先复用，再决定实现

新增或实质扩展能力时，先查仓库相邻实现、依赖和已有工具，再查相关官方或成熟开源方案。用适用性、维护成本、许可、平台和当前目标比较采用、适配与自研。已有同范围有效结论可复用；版本、授权或约束变化时只刷新受影响部分。

研究不足不能表述为“没有现成方案”。纯机械修改或事实已足够的局部修复无需反复外搜。资料和示例不能替代当前项目行为证据，研究也不授予安装依赖、付费或外部写入权限。

## 最小完整实现

每个新增抽象、配置项和依赖都应对应当前需求。完整意味着包含相关失败、取消、状态恢复和实际接入；不意味着预建未来平台、通用引擎或完整后台。

1. 明确输入、输出、状态、持久化和调用边界；不适用的层无需创建。
2. 从最小可验证切片实现，保持现有接口与已接受行为。
3. 修复 bug 先建立触发条件、预期与实际差异，追到真实运行路径；不只修未被调用的 helper。
4. 同时检查代码默认值、序列化数据、配置文件、后台和部署版本中实际生效的一层。
5. 保护其他人的未提交工作；不顺手格式化、升级依赖或重构无关模块。
6. 按 [verification.md](verification.md) 验证需求与失败边界，满足完成条件后停止扩大检查。

## 交付与接续

交付说明做了什么、验证了什么、关键缺口是什么。长任务只在已有阶段 owner 中保存当前对象、完成状态、证据、剩余工作、下一步和失效条件。不要把日志堆成另一份真相；写入按 [memory.md](memory.md)。
